# gaojia-assembly 本地存储设计

## 1. 接口关系分析

根据 [基本过程.md](/Users/ice7/Documents/temp/gaojia-assembly/基本过程.md) ，当前至少有 3 类核心数据：

1. 章节树接口
   `POST /napi/chapter/list/sub-240`
   作用：返回科目 `subject=240` 下的一级章节、二级章节，以及每个章节的统计信息。

2. 章节题目清单接口
   作用：返回某个章节下有哪些题目，包含：
   - `question_id`
   - `index`
   - `question_type`
   - `answer_type`
   - `belong_page`
   - `total_question`
   - `chapter_section_num`

3. 题目详情接口
   `GET /napi/exam/get-question?id=208435`
   作用：返回某道题目的完整信息，包含：
   - 题干 `title`
   - 选项 `option`
   - 正确答案 `answer`
   - 解析 `analyze`
   - 知识点 `knowledge`
   - 题型、难度、审核信息、更新时间等元数据

这 3 类接口之间的关系是：

- 一个科目下面有多个章节
- 一个章节下面有多道题
- 一道题在接口层面通过 `question_id` 唯一标识
- 章节题目清单是“章节和题目”的关联层
- 题目详情是“题目主数据”

因此本地库建议拆成：

- 科目表
- 章节表
- 章节题目关联表
- 题目主表
- 题目选项表
- 抓取批次/原始响应日志表

## 2. 设计目标

本地存储设计需要满足以下目标：

1. 能完整保存网站题库到本机
2. 能保留章节树结构
3. 能支持一个章节下题目列表的顺序信息
4. 能支持后续重新抓取并做增量更新
5. 能保留原始 JSON，方便排错和字段扩展
6. 能支持后续增加“做题记录”“错题本”“收藏”等本地功能

## 3. 实体关系

核心 ER 关系如下：

- `ag_subject` 1 -> N `ag_chapter`
- `ag_chapter` 1 -> N `ag_chapter_question`
- `ag_question` 1 -> N `ag_question_option`
- `ag_question` 1 -> N `ag_chapter_question`
- `ag_sync_batch` 1 -> N 各业务表（通过 `last_sync_batch_id` 追踪最近抓取来源）

说明：

- `ag_chapter` 使用自关联 `parent_chapter_id` 保存树结构
- `ag_chapter_question` 负责保存题目在章节中的顺序和页面位置
- `ag_question` 保存题目详情
- `ag_question_option` 将 `option` JSON 数组展开，便于检索和展示
- 各表可同时保存 `raw_json`，应对接口字段变化

## 4. 表设计说明

### 4.1 科目表 `ag_subject`

用途：

- 保存科目维度，例如 `subject=240`
- 方便后续支持多个科目

关键字段：

- `subject_code`：接口里的 `subject`
- `subject_name`：本地命名，可先人工维护

### 4.2 章节表 `ag_chapter`

用途：

- 保存一级、二级章节
- 保存章节统计信息

关键字段：

- `chapter_id`：接口 `id`
- `parent_chapter_id`：接口 `pid`
- `chapter_level`：1 表示一级，2 表示二级
- `all_question_num`、`do_question_num`、`right_question_num`
- `right_question_rate`：原始字符串，如 `62%`、`-`

### 4.3 章节题目关联表 `ag_chapter_question`

用途：

- 保存某章节下包含哪些题目
- 保存题目在章节内的顺序

关键字段：

- `chapter_id`
- `question_id`
- `question_index`
- `belong_page`
- `question_type`
- `answer_type`

约束建议：

- 唯一键：`(chapter_id, question_id)`

### 4.4 题目主表 `ag_question`

用途：

- 保存题干、答案、解析、知识点、题型、审核信息等

关键字段：

- `question_id`
- `title_html`
- `question_type`
- `show_type_name`
- `knowledge`
- `answer_json`
- `analyze_text`
- `difficulty_id`
- `updated_at_remote`

说明：

- `title` 和 `option` 明显带 HTML，建议原样保存
- `answer` 可能是多选数组，建议使用 JSON
- `option` 不建议只保存在主表里，最好拆到子表

### 4.5 题目选项表 `ag_question_option`

用途：

- 保存题目选项的展开结构

关键字段：

- `question_id`
- `option_no`：1,2,3,4...
- `option_label`：A,B,C,D...
- `option_html`

### 4.6 同步批次表 `ag_sync_batch`

用途：

- 记录每次抓取的执行情况
- 支持问题排查和重跑

关键字段：

- `batch_no`
- `sync_type`：`chapter_tree` / `chapter_questions` / `question_detail`
- `subject_code`
- `chapter_id`
- `question_id`
- `status`
- `response_raw`

## 6. 关键设计取舍

### 6.1 为什么章节和题目要拆成多张表

因为接口本身就是分层返回：

- 章节接口只负责章节树和统计信息
- 章节题目接口只负责“章节下有哪些题”
- 题目详情接口只负责题目主数据

如果全部塞进一张表，会导致：

- 字段大量重复
- 一个题目在多个章节出现时难以复用
- 增量更新非常麻烦

### 6.2 为什么要保留 `raw_json`

当前文档里字段较多，后续接口很可能继续扩展。
保留原始 JSON 有两个价值：

1. 抓取脚本升级时可回放历史数据
2. 某些暂时未建模的字段，后续可以补充解析

### 6.3 为什么单独做同步日志表

因为抓取程序不是一次性导入，而是长期同步任务。
如果没有批次表，很难知道：

- 哪次抓取失败
- 失败的是哪个章节或题目
- 某条数据最后一次是何时更新

## 7. 推荐抓取落库流程

建议按下面顺序写入：

1. 调章节树接口
2. 写入 `ag_subject`
3. 写入 `ag_chapter`
4. 逐个二级章节调题目清单接口
5. 写入 `ag_chapter_question`
6. 收集全部 `question_id`
7. 逐题调详情接口
8. 写入 `ag_question`
9. 解析 `option`，写入 `ag_question_option`
10. 每一步记录 `ag_sync_batch`

## 8. 后续可扩展表

如果后面还要做本地刷题功能，建议继续加：

- `ag_user_answer_record`：本地答题记录
- `ag_wrong_question`：错题本
- `ag_favorite_question`：收藏题
- `ag_sync_cursor`：增量抓取游标

当前第一版先不强制建这些表，先把题库主数据落稳。
